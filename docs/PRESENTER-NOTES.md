# 발표자 노트

발표 PPT(`hedwig-spam-gateway-intro.pptx`)용 말씀 자료와 예상 질문 답안. 슬라이드는 제목으로 찾는다(발표용으로 수정된 순서와 다를 수 있음).

## 발표 기조
- 우리는 후발 주자다. 혁신을 내세우지 않고 **"최소한 겹겹의 방어막이 있고, 효과를 측정해서 정직하게 운영한다"** 는 신뢰를 준다.
- 수치는 사내 코퍼스 분석 결과이지 서비스 성능 지표가 아니다.
- 피할 표현: "정확도가 올랐다", "RAG 덕분에 더 잘 잡는다", "AI가 스스로 학습한다", "무중단 failover".
- 쓸 표현: "안전망", "측정하고 결정했다", "사람이 최종 승인", "로드밸런싱".

## 슬라이드별 말씀 요지

| 슬라이드 | 말씀 |
|---|---|
| 표지 | Hedwig 본체를 수정하지 않는 독립 프로세스다. 오늘은 구조, 스팸 대응 방식, 관리 화면, 신고 흐름을 보여 드린다. |
| 왜 필요한가 | 사내 2개월 스팸 32,575건을 분석하니 64%가 자사 도메인 사칭이었다. 상용 장비 없이 Hedwig 앞단에서 기본 방어를 갖춘다. Java 8, jar 하나로 배포한다. |
| 메일이 지나가는 순서 | RBL → 그레이리스팅 → 화이트/블랙리스트 → 룰 → LLM 순서다. 스팸 판정은 차단이 아니라 헤더 표시이며, 검사 오류 시에는 메일을 통과시킨다(fail-open). 룰로 확정되면 LLM 호출을 생략해 비용을 아낀다. |
| 룰 엔진 | 사내 데이터로 룰을 키웠다(운영 193개). 보류 표본 1,169건에서 룰만으로 스팸 판정이 82건에서 291건으로 늘었고, 정상 대용 641건의 오탐은 8건에서 11건이었다. 라벨 한계가 있어 참고용 수치다. |
| LLM 판정과 RAG | 룰이 확정 못한 메일만 LLM이 본다. RAG는 같은 메일 200건으로 측정했더니 차이가 없어 기본을 꺼 두었다. 사용자 신고 사례를 쌓는 안전망으로 쓰고, 데이터가 쌓이면 다시 평가한다. |
| 가중치는 사람이 정한다 | 룰 적중 횟수와 마스킹 샘플을 보고, 판단이 어려우면 LLM 의견을 참고한다. 적용은 관리자가 확인창을 거쳐서만 된다. |
| 사용자 신고 흐름 | 그룹웨어가 신고 → 즉시 접수 → LLM 판정 → RAG 편입. 룰 추가는 수동 승인이 기본이고 자동은 좁은 조건에서만 한다. 신고 사유와 원본 메일(EML)도 받는다. |
| 관리자 대시보드 | 룰 관리, 스팸 신고, 화이트/블랙리스트 세 탭. ID/PW 로그인. |
| 보안 | 외부가 미리 달고 온 X-Spam-* 헤더는 판정 전에 제거한다(LLM이 위조 헤더에 속는 사례를 실제로 확인). 신고 본문은 신뢰하지 않는 외부 텍스트로 취급한다. |
| 멀티 인스턴스 로드밸런싱 | SO_REUSEPORT로 여러 인스턴스가 같은 포트를 공유하고, 상태는 Oracle로 공유한다. **현재 운영은 단일 인스턴스이며 다중 구동은 앞으로의 과제**라고 분명히 말한다. |
| 운영 구성 | egov 개발서버: 외부 25번 → 게이트웨이 → Hedwig 2599, DB는 Oracle 19c, LLM은 Gemini. |

## 예상 질문과 모범 답안

### RBL
- **무엇인가?** 스팸 발송 IP 블랙리스트를 DNS로 조회한다. 접속 IP를 뒤집어 `zen.spamhaus.org`, `bl.spamcop.net`에 질의하고, 올라 있으면 SMTP 시작 전에 연결을 끊는다.
- **장애 시 메일이 막히나?** 아니다. 타임아웃 3초, DNS 오류는 통과 처리(fail-open).
- **정상 서버가 올라 있으면?** 오탐이 가능하다. RBL은 연결 단계라 화이트리스트보다 먼저 적용되어 화이트리스트로 살릴 수 없다. 해당 존에서 빼는 방식으로 대응한다.
- **조회량은?** Spamhaus는 공용 리졸버와 대량 조회에 제한이 있어 트래픽이 많으면 자체 리졸버나 데이터 피드를 검토한다. 실트래픽 측정은 아직 하지 않았다.

### 그레이리스팅
- **원리?** (발신 IP, MAIL FROM, RCPT TO)를 처음 보면 `450`으로 임시 거절한다. 정상 서버는 재시도하고 스팸 봇은 대부분 안 한다. 5분 후 재시도하면 통과하고 30일간 신뢰한다.
- **단점?** 처음 보는 발신자의 첫 메일이 최소 5분 늦어진다. 재시도 때 IP가 바뀌는 대형 서비스는 더 늦어질 수 있고, 재시도 안 하는 시스템은 메일을 잃을 수 있다.
- **지연이 곤란한 상대는?** 화이트리스트에 넣으면 건너뛴다(그레이리스팅보다 먼저 확인).
- **다중 인스턴스에서는?** 상태를 DB에 두므로 재시도가 다른 인스턴스로 가도 같은 판단이 된다.

### RAG
- **포지셔닝(핵심):** "LLM 판정에 사내 스팸 사례를 근거로 붙이는 장치를 갖추고 있고, 효과는 직접 측정해서 판단합니다."
- **효과가 있었나?** 같은 메일 200건 비교에서 89.5~90.0% 대 89.0~89.5%로 차이가 없었다. 그래서 과장하지 않고 기본을 꺼 두었다.
- **그럼 왜 필요한가?** 현재 데이터로는 Gemini 단독과 차이가 없다고 측정됐다. 다만 고객사별 신고 사례가 쌓이면 그 환경에 특화된 판단 근거가 되고, 그때 효과를 다시 측정할 수 있는 구조를 미리 만들어 둔 것이다.
- **데이터가 외부로 나가나?** 임베딩 API 없이 자체 검색으로 동작하고, 저장 전에 이메일과 긴 숫자를 가린다. LLM(Gemini) 호출에는 마스킹된 발췌가 쓰인다.
- **평가의 한계?** 코퍼스 스팸 라벨에 노이즈가 있고, 정상 대용 일부가 실제 사칭 피싱이어서 오탐률은 신뢰하기 어렵다. 90%는 재현율의 하한이다.

### 스팸 룰 가중치
- **계산 방식?** 적중한 룰의 가중치 합이 5.0 이상이면 스팸. 단독 확정은 가중치 5 이상인 룰(자사 도메인 사칭 5.0)뿐이다.
- **누가 정하나?** 관리자. 새 룰은 1~2로 낮게 시작하고 적중과 샘플을 보며 조정한다. LLM 의견은 참고용이고 적용은 사람이 한다.
- **LLM이 자동으로 바꾸나?** 아니다. 신고 기반 자동 룰도 가중치 상한 2.0, 일일 20건 상한이 있어 단독으로 스팸을 확정하지 못한다.
- **오탐 관리?** 적중 대비 스팸 판정 횟수와 샘플을 보고 정상 메일이 섞이면 낮추거나 비활성화한다.
- **스팸이면 차단하나?** 헤더만 붙인다. Hedwig가 `X-Spam-Flag`로 스팸함 이동을 정한다.

### 기타
- **다중 인스턴스/무중단?** 로드밸런싱까지 설계했고 현재 운영은 단일 인스턴스다. 다중 구동 운영 검증은 앞으로의 과제이며, 완전 무중단은 범위 밖이다.
- **LLM 비용/장애?** 룰로 확정되면 LLM 호출을 생략한다. LLM 장애 시에는 정상 처리(fail-open).
- **개인정보?** 신고와 샘플은 이메일/긴 숫자를 가려 저장하고, 원본 EML은 LLM에 보내지 않으며 관리자만 내려받는다. EML 보관 기간 정책은 아직 정하지 않았다.

## 발표 전 점검
- egov에서 시연 메일/신고가 실제로 동작하는지 한 번 돌려 본다(그레이리스팅은 운영 설정이 5분이라 사전 준비 권장).
- 시연 중 만든 시험 룰과 신고는 끝나고 정리한다.
- Gemini 키, 관리자 키는 발표 환경 화면에 노출되지 않게 한다(교체도 권장).
